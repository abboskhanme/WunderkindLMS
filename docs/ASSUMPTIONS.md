## Phase 1 — P1-05, `BillingCore` migration + database guards (2026-09-11)

- [2026-09-11] How do the new money tables lose `UPDATE`/`DELETE` again, given `ALTER DEFAULT PRIVILEGES` hands every freshly created table to `app_rw` with full CRUD — (a) `REVOKE` inside the migration, or (b) re-run `deploy/init-roles.sql` after every migration (the P1-02 decision)? → **both, with (a) as the primary** → (b) alone is a manual step that produces *no error when forgotten*: the app keeps working and the money protection is simply gone. (a) makes the protection arrive in the same transaction as the `CREATE TABLE`, so it cannot be forgotten. (b) stays because it also covers `access_events` / `point_transactions` (Phase 2 and 4), refreshes passwords, and prints the `owns_in_public = 0` evidence line. The P1-02 entry above is extended, not superseded. Verified: `update payments set amount = 1` as `app_rw` → SQLSTATE 42501, row survives.
- [2026-09-11] The migration's GRANT/REVOKE block when the `app_rw` role does not exist (test harness, pre-P1-02 databases) → **skip with a `RAISE NOTICE`, do not fail** → the DDL has already been applied by that point, so failing would leave a half-migrated database. The notice says plainly that the database has no financial immutability and points at `init-roles.sql`.
- [2026-09-11] Where does the raw SQL live — inline C# string in the migration, or a `.sql` file? → **`.sql` file embedded as an assembly resource (`Migrations/Sql/*.sql`, read by `Migrations/MigrationSql.cs`)** → 120 lines of trigger and grant logic inside a C# string literal cannot be reviewed: no syntax highlighting, escaped quotes, one-line diffs. Financial protection has to be readable. An embedded resource (not a file on disk) is required because migrations run in the published container, where the source tree does not exist; a missing resource throws loudly instead of silently skipping the guards.
- [2026-09-11] `DROP TRIGGER IF EXISTS` before `CREATE TRIGGER` (the usual idempotency idiom)? → **no — `CREATE OR REPLACE TRIGGER` (PostgreSQL 14+, stack is 17)** → P1-05's acceptance criterion is that `dotnet ef migrations script` contains zero `DROP`. Keeping that rule absolute is what makes "a `DROP` in `Up()` means stop and read" a usable habit; one tolerated `DROP` and the check stops being scannable. The table is created in the same migration, so the trigger cannot pre-exist anyway.
- [2026-09-11] The allocation trigger in SPEC §3.7 has a concurrency hole (two parallel transactions each see only committed allocations, so both can pass and the payment gets allocated twice). Fix with `SELECT ... FOR UPDATE` on `payments`? → **no — `pg_advisory_xact_lock(hashtextextended(payment_id::text, 0))`** → `SELECT ... FOR UPDATE` requires the `UPDATE` privilege on `payments`, which `app_rw` deliberately does not have; the lock would therefore fail with 42501 for the very role that needs it. The alternative, a `SECURITY DEFINER` function, adds a privilege-escalation surface for no gain. An advisory lock needs no table privilege and is released at commit.
- [2026-09-11] Seed (five fee categories + the settings row): EF `HasData`, application startup, or SQL in the migration? → **SQL in the migration, with hand-written stable UUIDs, `ON CONFLICT DO NOTHING`** → `HasData` would make the rows part of the model, so a later edit to a category name becomes a migration. Startup seeding would need `app_rw` to insert reference data. Stable ids (`…c1`…`…c5`, `…b1`) matter because a category id read from a production log has to be findable in a local database.
- [2026-09-11] How is "`app_rw` cannot UPDATE/DELETE `payments`" proven, given the test harness deliberately does not create `app_rw` (docs/TESTING.md §4)? → **`tools/verify-billing-guards.sh`** → it starts a throwaway Postgres 17, applies the real `deploy/init-roles.sql` at initdb time, runs the migration as `schoollms_owner`, and then asserts 42501 plus the trigger, the dual-control constraint, the single-open-shift index, seed idempotency and "zero `DROP` in the migration script". This reproduces the production path exactly, which the in-process harness by design cannot. It does not replace P1-22 — see the handoff note in `docs/TESTING.md`.

## Phase 1 — P1-07, `LedgerService` (2026-09-11)

- [2026-09-11] `ReverseAsync` takes ONE `entryId`, but reversing a single line of a balanced set would leave the journal unbalanced. How is the set identified, given the schema has no batch column and is now frozen? → **a posting batch is `(ref_type, ref_id)`; `PostAsync` refuses a call whose lines disagree on either, and stamps a synthetic `ref_id` when the caller has none (manual adjustment)** → this makes every batch identifiable without a schema change, so `ReverseAsync` can mirror the whole set. The index `ix_ledger_entries_ref_type_ref_id` already supports the lookup. The constraint "one call = one business event" is a real modelling rule, not a workaround: a caller needing two events calls twice.
- [2026-09-11] Reversal entries: keep the original `ref_type`, or use `reversal`? → **`ref_type = 'reversal'`, `ref_id` = the original's** → the reversal lines then fall outside the original batch's own `(ref_type, ref_id)` query, so "find the batch" and "has it been reversed" stay two simple, non-overlapping questions. `reversal_of` still points at the individual original line.
- [2026-09-11] The reversal's `entry_date`: the original's date, or today? → **today** → back-dating a correction into a period that has already been reported silently rewrites a number somebody has already read. The correction belongs to the day it was made.
- [2026-09-11] Rounding: reject amounts with more than 2 decimals, or round them? → **round to 2 decimals first, then check the balance on the rounded values** → the column is `numeric(14,2)`, so validating the unrounded values would let a set that balances in memory be stored unbalanced. Rounding first means what is validated is exactly what is persisted; if rounding breaks the balance the caller gets a loud error rather than a silent half-tiyin drift.
- [2026-09-11] Dual control on `ReverseAsync` → **the approver may not be any of the batch's authors** → SPEC §4.5 lists payment reversal and manual ledger adjustment as always requiring a second person. Checking every line's `created_by` (not just the anchor's) closes the case where a batch was somehow written by two people.
- [2026-09-11] `AppClock` needed an offset-aware accessor for the new `timestamptz` columns; the first attempt returned UTC+5 and Npgsql rejected it (`"only offset 0 (UTC) is supported"`). → **`AppClock.NowInstant` returns `DateTimeOffset.UtcNow`, plus `ToLocal` / `LocalDateOf` for display and day-grouping** → `timestamptz` stores an instant, not an offset, so UTC is the correct and only accepted representation. Putting it on `AppClock` (one additive property) rather than leaving each Phase 1.C service to convert for itself is the point: five agents writing five conversions would produce five subtly different ones.
- [2026-09-11] `LedgerService.PostAsync` calls `SaveChangesAsync` itself, so a payment write (P1-11) would be two commits. → **added `BeginTransactionAsync` to `IAppDbContext`** → a crash between the two commits would leave a payment with no ledger entry, which is exactly the kind of discrepancy nobody can reconstruct afterwards. The alternative (making the caller save) would have let a standalone `PostAsync` silently do nothing. Recorded for Phase 1.C in `docs/PENDING_WIRING.md`.
- [2026-09-11] `Accounts.SettlementFor(method)` (cash → `cash`, everything else → `bank`) is defined by delegating to `PaymentMethod.CountsAsCash` rather than by its own `switch` → "is this cash?" must have exactly one answer in the codebase; the shift's `expected_cash` and the ledger posting have to agree or every shift shows a phantom variance.
- [2026-09-11] `LedgerService` is not registered in DI → **deliberate; recorded in `docs/PENDING_WIRING.md` for P1-15** → `Program.cs` is P1-15's file and Phase 1.B should not start claiming it. Nothing breaks at build time; the first controller that injects `ILedgerService` fails at request time until the one line is added.

## Phase 1 — P1-08, fee catalog, subscriptions, discounts (2026-09-11)

- [2026-09-11] `docs/TASKS.md` P1-08 still says "a discount above the configured threshold returns `409 approval_required`", and names a default threshold of 20 % / 500 000 so'm. → **No threshold exists. Every discount is created `pending` and the create response is `200` with `status = "pending"`, never 409** → client answer SPEC §8.1 Q5 supersedes the task text: *"Every discount needs the director's approval — no threshold."* With a threshold, a below-threshold discount took effect immediately; without one, a discount is inert from birth, so waiting for approval is the normal flow, not an exception — and 409 is the wrong code for a normal flow. Accrual (P1-09) filters on `status = 'approved'`; `ck_discounts_approved_has_approver` and `ck_discounts_approver_differs` back it in the database.
- [2026-09-11] Approval is restricted to `superadmin` by `[FinanceRole(FinanceAction.ApproveDiscount)]`. Should `DiscountService` check the role again? → **yes — it loads the approver and rejects a non-`superadmin` with `approver_not_director`** → the controller attribute is one line that a later refactor or a new endpoint can omit without any test noticing. A money rule must not depend on one layer remembering. Same argument for the self-approval check, which exists in three places: the service, the DB check constraint, and the §4.3 matrix.
- [2026-09-11] `RejectDiscountRequest.Reason` has nowhere to go: `discounts` has no `decision_note` column (schema frozen in P1-05) and `DiscountDto` has no field for it. Overwrite `discounts.reason`? → **no — the rejection reason goes to `audit_log` only** → `discounts.reason` is the *requester's* justification; overwriting it destroys why the discount was asked for, which is the one thing the director needs when the same request comes back next month. The frozen DTO cannot show a rejection reason anyway, so audit is the only honest home for it.
- [2026-09-11] On reject, is `approved_by` set to the rejecting director? → **yes; the column means "who decided"** → otherwise a rejected row records no decision-maker at all, and the DB constraint `approved_by <> created_by` is enforced for rejection too. Consequence, accepted deliberately: a director cannot reject a discount they requested themselves; they leave it pending instead.
- [2026-09-11] "The first tuition subscription is pre-filled from `SchoolClass.MonthlyFee`" — where does the pre-fill happen, given `CreateSubscriptionRequest.MonthlyAmount` is a non-nullable `decimal` so "omitted" and "zero" are indistinguishable? → **both: `GET /api/admin/billing/subscriptions/default` returns the suggestion for the form, and `CreateAsync` falls back to the class fee when the amount is 0, the category is `tuition`, and the student has no tuition subscription yet** → the endpoint is the primary path (a pre-fill is a UI act). The server-side fallback exists because a zero-price tuition subscription would otherwise be a way to make a student free *without the director's approval*, which is precisely the hole Q5 closes — free tuition is a 100 % discount, and that needs a signature. The substitution is never silent: the response DTO returns the stored amount and the audit line names the source ("summa manbai: 8-A sinfining oylik to'lovi"). Only the **first** subscription in the category gets a suggestion; after that the price lives on the subscription and a class-fee change no longer moves it — raising a class fee must not silently re-price 300 existing contracts.
- [2026-09-11] Overlapping subscriptions: where is "one price per (student, category, month)" enforced? → **in `SubscriptionService` only, for now** → the database equivalent is an `EXCLUDE USING gist` constraint that needs the `btree_gist` extension and therefore a migration, and P1-08 owns no migration file. Recorded in `docs/PENDING_WIRING.md` §10 for the next migration owner. This is a genuine gap under concurrency, not a design choice.
- [2026-09-11] `ISubscriptionService` has no frozen counterpart in `IBillingServices.cs` (P1-06 froze five interfaces; subscriptions was not one). → **the interface is declared in `SchoolLms.Application/Billing/SubscriptionService.cs`** → adding a type to the frozen file would have collided with the four other Phase 1.C agents editing in parallel, for the same reason `Billing.cs` was split from `Entities.cs`. Every other P1-06 convention is kept: DTOs from `Dtos.Billing`, `actorId` as a separate parameter, no generic CRUD.
- [2026-09-11] How does a service-layer rule violation become an HTTP status, given the project has no exception-to-status convention? → **a dedicated `BillingRuleException` (fault kind + machine code) plus a `[BillingFault]` exception filter** → the obvious alternative, catching `InvalidOperationException` in the controller, would also catch "Unable to resolve service for type `IDiscountService`" — the exact state of the app until P1-15 wires DI — and report a broken deployment as a 409 business response. The fault kind is an enum, not an HTTP number, so the Application layer stays HTTP-free (SPEC §2.2). Error body is `{code, message}` and not `ProblemDetails`, because the whole frontend reads `err.response.data.message`.
- [2026-09-11] Filtering discounts by `categoryId`: return only rows with that `category_id`, or also the global ones (`category_id is null`, "all categories" per SPEC §3.7)? → **also the global ones** → the filter answers "which discounts *apply to* this category", which is what accrual (P1-09) needs. The narrow reading would make a global discount invisible to the per-category accrual and silently overcharge the student.
- [2026-09-11] A cashier reading the catalog — allowed? → **no: the whole controller is `[Authorize(Roles = Roles.FinanceStaff)]` (admin + superadmin), reads included** → SPEC §4.3 has no row granting the cashier anything here, not even read. The acceptance criterion only demanded 403 on writes; denying reads as well follows the table rather than inventing an allowance it does not contain.
- [2026-09-11] EF could not translate `Where`/`OrderBy` applied after a constructor projection (`select new DiscountDto(...)`) — it throws at query time, not at build time, and the first test run hit it on 20 tests. → **filter and sort on the entity columns, project into an anonymous type inside the same query, build the DTO in memory after `ToListAsync`** → still one SQL statement with the sort done by the database, and no N+1; the DTO constructor simply stops being part of the expression tree. Noted here because the failure mode (compiles fine, dies at runtime) will bite P1-09…P1-12 writing the same kind of projection.
- [2026-09-11] `BillingCatalogTests` needs the two services in DI to test the happy path over HTTP, but `Program.cs` belongs to P1-15. → **a derived factory in the test file (`fixture.Api.WithWebHostBuilder(… AddScoped …)`)** → touching `Fixtures/ApiFactory.cs` would have put P1-08 into a file the other parallel tasks also use. The RBAC tests need no such thing: authorization filters run before the controller is constructed, so 401/403 are already reachable today.

## Phase 1 — P1-09, invoices + per-category accrual (2026-09-11)

- [2026-09-11] A student has two approved discounts that both apply to one invoice (one for the category, one for "all categories") — stack them, or pick one? → **pick one: the most specific wins (category-specific over global), ties broken by the later `starts_on`, then `created_at`** → the legacy model had exactly one discount per student (`Student.DiscountPct` + `.DiscountAmount`, applied together), so "one winning row" reproduces today's figures, which P1-23 has to match. Silent stacking would also let two innocent-looking 60 % approvals add up to a free year, and the director who approved the second one would never see it.
- [2026-09-11] An invoice whose payable is 0 (100 % discount, or a free subscription) → **the row is still written, its status derives to `paid`, and it gets NO ledger pair** → the journal rejects a zero-amount line (`ck_ledger_entries_amount: amount > 0`) and rightly so: there is no receivable and no revenue to record. Dropping the invoice row instead would hide the student from the monthly report, which is the opposite of what a 100 % discount should do — the legacy `AccrueMonth` kept the row for the same reason.
- [2026-09-11] `invoices.status` at creation: set `'open'` literally, or derive it? → **always derived, `InvoiceService.StatusFor(payable, allocated)`, including at creation (allocated = 0)** → the acceptance criterion is "status moves `open → partial → paid` from allocation totals only; nothing sets it directly". One function means P1-11 cannot invent a second, subtly different rule when it records a payment; it also makes the zero-payable case fall out of the arithmetic instead of needing a special case.
- [2026-09-11] `entry_date` of the accrual's ledger pair: today, or the month being accrued? → **the first day of the accrued month** → a July month back-filled in September belongs to July's P&L. Booking it in September would make the monthly income report depend on when the job happened to run, and nobody could reconcile the two afterwards. (The *reversal* of such a pair still books today — that rule was set in P1-07 and is unchanged.)
- [2026-09-11] The accrual job is unattended, but `ledger_entries.created_by` is `not null` and references `users(id)` (SPEC §4.4). Who is the author? → **the first `superadmin` by id, falling back to `admin`; with neither, the tick is skipped with a warning** → a dedicated `system` user would read better in the journal but needs a migration, and the migration chain is a shared file that P1-09 may not touch. Recorded for P1-15 in `docs/PENDING_WIRING.md`. A database with no admin also has no subscriptions, so the skipped tick loses nothing.
- [2026-09-11] Two subscriptions for the same `(student, category)` overlap one month (the old one ended on the 10th, the new one started on the 11th) — the unique index allows only one invoice. → **the one with the later `starts_on` wins, i.e. the current price** → charging the superseded price for the month the price changed is the version that generates a complaint. P1-08 already rejects overlapping *active* subscriptions, so this only arises for a genuine mid-month switch.
- [2026-09-11] Does a payment that was later reversed still count toward an invoice's `paid`? → **no — `PaidByInvoiceAsync` excludes both the reversal row and the payment it reverses** → `payment_allocations.amount > 0` is a check constraint and the table is insert-only, so a storno can neither write a negative allocation nor delete the original one. The only correct place to undo it is the query that sums allocations; doing it anywhere else would leave a reversed payment looking like it still cleared the debt.
- [2026-09-11] "Overdue" boundary when the admin changes `overdue_after_day` after invoices already exist → **`max(invoice.due_on, overdue_after_day of that period month)`** → reading the setting live is what the client asked for (Q6), but lowering it must not make an invoice overdue *before* the due date printed on it. The floor keeps the two settings from contradicting each other on historical rows.
- [2026-09-11] `InvoiceQuery` (frozen in P1-06) has no paging, and an unfiltered list is ~36 000 rows for a full school year. → **`ListAsync` orders newest-month-first and caps at `MaxListRows = 2000`** → returning everything is how a finance page becomes a 30-second request. A cap silently truncates, which is why it is written in the XML doc, in `docs/PENDING_WIRING.md` and here: the real fix is two optional fields on `InvoiceQuery`, which the frozen-contract rules explicitly allow as additive.
- [2026-09-11] Where does the discount formula live, given P1-08 (`DiscountService`) and P1-09 (accrual) were written in parallel and P1-09 may create only two files? → **`DiscountMath` (static) at the bottom of `InvoiceService.cs`; P1-08 delegates to it** → injecting `IDiscountService` into the accrual would have made P1-09 unbuildable and untestable until P1-08 merged. A static helper keeps exactly one copy of the arithmetic, which is the only property that actually matters here.
- [2026-09-11] `VoidAsync` order of operations: mark the row `void` first, or reverse the ledger first? → **ledger first** → `LedgerService.ReverseAsync` enforces dual control (§4.5) and throws when the person voiding is the one who ran the accrual. With the status set first, the database rolls back correctly but EF leaves the *tracked* entity as `void` in memory, so the next (legitimate) attempt on the same context fails with "already voided" while the row is alive in the database. Caught by `Bekor_qilingan_oy_…` before it reached anyone.
- [2026-09-11] Which months does `AccrueDueAsync` fill? → **`AcademicYearStartMonthAsync` … current month, extended backwards if a subscription starts earlier** → same shape as the legacy `AccrueDue` (which extended backwards for early enrolments), and it reuses `TuitionService.MonthRange` / `NextMonth` unchanged as TASKS.md §1.3 requires. Months where no subscription is active produce zero rows, so the extra iterations are cheap.
- [2026-09-11] Test isolation for accrual tests, given the suite shares one database → **each test creates its own database from the migrated template (~100 ms)** → accrual counts every subscription in the database, so "how many invoices were written" would otherwise depend on other tests' students; and the due-date test *updates* the single `billing_settings` row, which would quietly change the figures P1-10 and P1-11 assert later.
