## Phase 1 — P1-02, DB role separation (2026-09-11)

- [2026-09-11] Two roles (SPEC §4.1) or three? → **three**: `schoollms` (bootstrap superuser, kept), `schoollms_owner` (schema owner, migrations), `app_rw` (the app) → SPEC §4.1 says the owner "is the existing `schoollms` role", but that role is the initdb SUPERUSER — a superuser bypasses `REVOKE` even harder than an owner does. `pg_isready`, `pg_dump` and break-glass access still need it, so it stays and is simply never used by the app. TASKS.md P1-02 already names `schoollms_owner`, so the two documents now agree.
- [2026-09-11] How do new tables created by a future migration lose `DELETE` again? → `deploy/init-roles.sql` is re-run after every migration, as a documented mandatory deploy step → `ALTER DEFAULT PRIVILEGES` grants full CRUD on new tables, so `payments` will arrive in P1-04 with `DELETE` granted. A DB `EVENT TRIGGER` could automate it, but it fires as the table owner and would be invisible machinery that nobody at 3am can debug. A re-run is one line in `deploy/README.md`.
- [2026-09-11] Migration stays automatic on container start (my own DevOps rule says it should be its own step) → keep auto-migrate, but add `Database:AutoMigrate` (default `true`) → flipping it to `false` today would break the existing deploy flow for zero benefit while there is no money in the schema. The flag makes the split a config change, not a code change, when P1-04 lands. Documented in `deploy/README.md`.
- [2026-09-11] Should `app_rw` also lose write access to `__EFMigrationsHistory`? → **no, not in P1-02** → it would be good hardening, but it turns the dev fallback (`Migrator` unset → migrate on `Default`) into a startup failure, and the task explicitly requires that fallback to keep working. Revisit in P1-22 together with the integration test.
- [2026-09-11] Migrator connection uses `Pooling=false` → yes → otherwise Npgsql keeps an idle, fully privileged schema-owner connection open for the entire process lifetime (observed in `pg_stat_activity` during verification) and burns one of the 60 connection slots on the 3 GB server. Migration is a one-shot job; pooling buys nothing.
- [2026-09-11] `deploy/init-roles.sql` reads passwords via psql `\getenv` → requires PostgreSQL 16+ → the stack is pinned to `postgres:17-alpine`, verified working. Keeps secrets out of the SQL file and out of git. If the image is ever downgraded below 16 this script fails loudly at `\getenv`, which is the correct outcome.

## Phase 1 — P1-04, billing entities + `cashier` role (2026-09-11)

- [2026-09-11] Where do the two configurable payment-date settings (client Q6: `payment_due_day`, `overdue_after_day`) live — new columns on `SchoolMeta`, or their own table? → **own table `billing_settings`, single row, fixed id `…0000b1`** → two reasons, either alone sufficient. (1) `SchoolMeta` lives in `Entities.cs`, and P1-04's acceptance criterion is literally "the diff of `SchoolLms.Domain/Entities.cs` is empty" — five agents write billing code in parallel in Phase 1.C. (2) `SchoolMeta` is already a 40-column grab bag (Telegram token, turnstile password, GPS radius); putting money settings in it would blur the "who may write to a finance table" question that P1-22 has to answer. Adding a setting later is a one-column additive migration.
- [2026-09-11] Billing timestamps: `DateTime` (like every existing entity) or `DateTimeOffset`? → **`DateTimeOffset` → `timestamptz`** → `AppDbContext.OnModelCreating` forces *every* `DateTime` column to `timestamp without time zone`, because the legacy code stores Tashkent wall-clock time. That is wrong for money: `received_at` and shift boundaries without an offset make a Z-report impossible to recompute, and SPEC §7 requires `timestamptz`. The existing loop only matches `DateTime`, so `DateTimeOffset` sidesteps it without touching a single legacy column.
- [2026-09-11] `payments.method` allowed values: SPEC §3.7 SQL says `cash|card|transfer`, client answer Q13 adds Payme/Click/Uzum → **four labels: `cash|card|transfer|online`** → the client answer is newer and explicit. `online` is a *label only* — no provider integration in this or any later phase. Only `cash` counts toward `expected_cash` at shift close.
- [2026-09-11] `discounts` needs a `status` column that SPEC §3.7 does not have → **added `status` (pending|approved|rejected) + `decided_at`** → client answer Q5: every discount needs the director's approval, no threshold. A discount is inert until `approved_by` is set, so accrual filters on `status = 'approved'`. Two DB constraints back it: `approved_by <> created_by` (SPEC §4.5) and `status <> 'approved' or approved_by is not null`.
- [2026-09-11] Check constraints and the `variance` generated column: raw SQL in the migration (as TASKS.md P1-05 lists them) or the EF model? → **EF model (`BillingModel.cs`), raw SQL only for what EF cannot express** → anything in the model lands in the snapshot, so a later `--autogenerate` leaves it alone; anything added by raw SQL is invisible to EF and can be silently dropped by a future migration. Only the allocation trigger and the GRANT/REVOKE stayed raw.
- [2026-09-11] EF configuration for 10 billing entities inside `AppDbContext.OnModelCreating`? → **separate `BillingModel.Apply(b)` in `Infrastructure/Data/BillingModel.cs`, one call site** → same argument that put the entities in `Billing.cs`: `AppDbContext` is a shared file and Phase 1.C is parallel. `AppDbContext` keeps the DbSets (they must be there) and one line of configuration.
- [2026-09-11] `Roles.Cashier` and token revocation → **added `cashier` to the `OnTokenValidated` branch in `Program.cs` (one line)** → without it a cashier fell into the `else { blocked = false; }` arm, so a *deleted* cashier would keep taking payments with an old token. `Program.cs` is P1-15's file, but shipping a money role with broken revocation is not an option; the change is additive and flagged to P1-15's owner.
- [2026-09-11] FK behaviour from billing rows to `users(id)` → **`DeleteBehavior.Restrict` everywhere** → a user who has taken money, approved a discount or posted a ledger entry can no longer be deleted. That is the correct audit behaviour (SPEC §4.6) and it costs nothing today because no billing rows exist yet. `StaffController.Delete` will start returning an FK error for such users once they do — deliberate.
- [2026-09-11] Extra DB guarantees not named in SPEC but cheap and load-bearing → **added**: partial unique index `ux_cash_shifts_one_open_per_cashier` (SPEC §4.2 says a cashier cannot open a second shift — now the database says it, not just the service), and a partial unique index on `payments.reversal_of` (a payment can be reversed at most once; without it the same payment could be "refunded" twice).

## Phase 1 — P1-05, `BillingCore` migration + database guards (2026-09-11)

- [2026-09-11] How do the new money tables lose `UPDATE`/`DELETE` again, given `ALTER DEFAULT PRIVILEGES` hands every freshly created table to `app_rw` with full CRUD — (a) `REVOKE` inside the migration, or (b) re-run `deploy/init-roles.sql` after every migration (the P1-02 decision)? → **both, with (a) as the primary** → (b) alone is a manual step that produces *no error when forgotten*: the app keeps working and the money protection is simply gone. (a) makes the protection arrive in the same transaction as the `CREATE TABLE`, so it cannot be forgotten. (b) stays because it also covers `access_events` / `point_transactions` (Phase 2 and 4), refreshes passwords, and prints the `owns_in_public = 0` evidence line. The P1-02 entry above is extended, not superseded. Verified: `update payments set amount = 1` as `app_rw` → SQLSTATE 42501, row survives.
- [2026-09-11] The migration's GRANT/REVOKE block when the `app_rw` role does not exist (test harness, pre-P1-02 databases) → **skip with a `RAISE NOTICE`, do not fail** → the DDL has already been applied by that point, so failing would leave a half-migrated database. The notice says plainly that the database has no financial immutability and points at `init-roles.sql`.
- [2026-09-11] Where does the raw SQL live — inline C# string in the migration, or a `.sql` file? → **`.sql` file embedded as an assembly resource (`Migrations/Sql/*.sql`, read by `Migrations/MigrationSql.cs`)** → 120 lines of trigger and grant logic inside a C# string literal cannot be reviewed: no syntax highlighting, escaped quotes, one-line diffs. Financial protection has to be readable. An embedded resource (not a file on disk) is required because migrations run in the published container, where the source tree does not exist; a missing resource throws loudly instead of silently skipping the guards.
- [2026-09-11] `DROP TRIGGER IF EXISTS` before `CREATE TRIGGER` (the usual idempotency idiom)? → **no — `CREATE OR REPLACE TRIGGER` (PostgreSQL 14+, stack is 17)** → P1-05's acceptance criterion is that `dotnet ef migrations script` contains zero `DROP`. Keeping that rule absolute is what makes "a `DROP` in `Up()` means stop and read" a usable habit; one tolerated `DROP` and the check stops being scannable. The table is created in the same migration, so the trigger cannot pre-exist anyway.
- [2026-09-11] The allocation trigger in SPEC §3.7 has a concurrency hole (two parallel transactions each see only committed allocations, so both can pass and the payment gets allocated twice). Fix with `SELECT ... FOR UPDATE` on `payments`? → **no — `pg_advisory_xact_lock(hashtextextended(payment_id::text, 0))`** → `SELECT ... FOR UPDATE` requires the `UPDATE` privilege on `payments`, which `app_rw` deliberately does not have; the lock would therefore fail with 42501 for the very role that needs it. The alternative, a `SECURITY DEFINER` function, adds a privilege-escalation surface for no gain. An advisory lock needs no table privilege and is released at commit.
- [2026-09-11] Seed (five fee categories + the settings row): EF `HasData`, application startup, or SQL in the migration? → **SQL in the migration, with hand-written stable UUIDs, `ON CONFLICT DO NOTHING`** → `HasData` would make the rows part of the model, so a later edit to a category name becomes a migration. Startup seeding would need `app_rw` to insert reference data. Stable ids (`…c1`…`…c5`, `…b1`) matter because a category id read from a production log has to be findable in a local database.
- [2026-09-11] How is "`app_rw` cannot UPDATE/DELETE `payments`" proven, given the test harness deliberately does not create `app_rw` (docs/TESTING.md §4)? → **`tools/verify-billing-guards.sh`** → it starts a throwaway Postgres 17, applies the real `deploy/init-roles.sql` at initdb time, runs the migration as `schoollms_owner`, and then asserts 42501 plus the trigger, the dual-control constraint, the single-open-shift index, seed idempotency and "zero `DROP` in the migration script". This reproduces the production path exactly, which the in-process harness by design cannot. It does not replace P1-22 — see the handoff note in `docs/TESTING.md`.
